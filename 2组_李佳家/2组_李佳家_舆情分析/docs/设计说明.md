# 舆情分析平台 · 设计说明

## 1. 项目定位

本项目实现需求文档 2.2「舆情分析平台」：面向指定主题，从公开信息、多媒体内容与内部沉淀数据三个方向收集信息，经过确定性 Agent 流水线生成可追溯的结构化舆情报告与关系图谱，并提供系统/应用/论坛/配置/状态的可视化控制台。

- 单功能应用：`topic_search`、`multimedia_search`、`insight_analysis`、`forum_collector`、`report_writer`
- 系统状态：`offline / starting / online / shutting_down`
- 应用状态：`stopped / starting / running / stopping / failed`
- 论坛状态：`idle / running / stopped / failed`
- 固定端口：`8714`
- 完全离线：不调用大模型 API，不依赖 CDN、外部字体或外部图片

### 关键设计决策

1. **应用工厂 + app.state**：`create_app(root, data_dir)` 将配置、存储、进程管理、流水线全部挂在 `app.state`，便于测试时用 `tmp_path` 完全隔离，也避免全局可变状态。
2. **文件为唯一事实来源**：报告、图谱、日志、输出都可从磁盘恢复；服务重启后报告列表、图谱列表、论坛历史仍可回查。
3. **线程模型**：FastAPI 同步接口运行在线程池；应用状态切换、系统启停、论坛采集使用守护线程；WebSocket 广播通过 `EventBus` 保存主事件循环并用 `call_soon_threadsafe` 投递。
4. **确定性 Agent**：不引入随机性或大模型；同一主题与来源集合产生稳定结论，便于测试与验收。
5. **引用可追溯**：来源按影响力分配 `[S01]` 引用编号；报告每个章节、风险点、结论建议均带引用，图谱节点/边也保存 `source_refs`。

## 3. 系统与进程状态机

### 3.1 系统

```
offline ──start──▶ starting ──0.25s──▶ online
   ▲                                     │
   │                                  shutdown
   └──── 0.2s ◀── shutting_down ◀────────┘
```

- `initialize()` 在 lifespan 启动时执行：初始化目录、配置、资源采样，按 `system.auto_start_system` 自动上线，按 `auto_start_apps` 启动应用。
- 关闭整体服务会停止论坛线程与所有应用，但**不删除**日志、报告与输出。

### 3.2 单功能应用

```
stopped ──start──▶ starting ──0.3s──▶ running
   ▲                                    │
   │                                 stop
   └──── 0.2s ◀── stopping ◀────────────┘
任意状态 ──异常──▶ failed（保留 last_error 与 stderr 日志）
```

- 启动/停止请求立即返回（可带 `?wait=1` 等待稳定），状态流转写入 `transitions` 并在 `/api/status` 中返回。
- 停止后 `manual_stop=true`，检索流水线不会自动拉起手动停止的应用，接口返回 409 并列出缺失应用；显式再次启动会清除该标记。
- 每个应用独立 `runtime/apps/{app}.log`，日志行格式：
  `2026-10-24 15:44:02.118 [INFO] [stdout] message`，错误写 `[ERROR] [stderr]`。
- `outputs/{app}/latest.txt` 保存最近一次任务输出，控制台显示摘要，弹窗显示完整日志。

### 3.3 论坛采集

- `idle` 初始；`start` 后启动守护线程并立即写入 10 条首轮引导日志（task_start、source_connected、keyword_loaded、batch_start、filter、sentiment、collect_post、save、archive）；
- 之后线程每 **1.5-3 秒**追加一条，事件类型在 collect_post / keyword_hit / sentiment / filter / save / archive 间轮换；
- `stop` 设置停止事件并 join 线程，追加 `task_stop`，状态置 `stopped`，此后不再追加；
- 每条记录包含 `time / event_type / message / task_status`，写入 `latest.log`（JSON Lines）并追加到 `history/{YYYY-MM-DD}.json`。

## 4. Agent 流水线

`POST /api/search` 触发。若 `runtime.require_apps_running=true`，先确保 4 个分析应用运行（用户手动停止的除外）。

| 顺序 | Agent | 应用 | 主要动作 | 输出指标 | 典型耗时 |
| --- | --- | --- | --- | --- | --- |
| 1 | 多来源检索 collector | topic_search | 主题/别名/关键词匹配，来源类型筛选，读取 30 天样例，分配 `[Sxx]` | 来源数、类型分布、时间跨度 | 30-80 ms |
| 2 | 多媒体解析 multimedia | multimedia_search | 图片 OCR、视频 ASR 文本抽取，平台/时长统计 | 素材数、OCR/ASR 条数 | 20-50 ms |
| 3 | 洞察分析 analyzer | insight_analysis | 情绪聚合、7 天趋势、渠道统计、角色观点、风险评分、证据挑选、结论 | 负面占比、观点组、风险分 | 25-70 ms |
| 4 | 报告生成 reporter | report_writer | 事件概述、时间线、渠道、观点、情绪、风险、证据、结论 + Markdown | 章节数、引用数 | 100-450 ms |
| 5 | 图谱构建 graph | report_writer | 主题/事件/实体/来源节点，关系边，统计并推送 `graph_ready` | 节点数、边数 | 120-280 ms |

每一步写入对应应用日志与输出，响应 `agent_steps` 包含 `title/status/duration_ms/summary/metrics`，前端渲染步骤条与总耗时。

### 4.1 主题匹配

- 数据集按 `topic`、`aliases`、来源 `keywords` 评分，精确主题 > 别名包含 > 关键词命中；
- 未命中返回 404，并列出可用主题；
- 过滤后无来源返回 404；
- 来源按 `influence` 降序分配 `S01...` 引用，展示时按发布时间降序。

### 4.2 分析规则

- **情绪**：positive / neutral / negative 计数与占比；负面 ≥45% 判“整体偏负”，负面高于正向判“中性偏负”；近 7 天与前期按影响力加权对比给出升/降/平台期。
- **渠道**：按 5 类来源统计数量、占比、负面占比、代表来源、引用编号。
- **观点**：按 `author_role` 分组；负面 ≥50% 为“质疑/担忧”，正向 ≥50% 为“认可/支持”，否则“理性观望”；摘要取组内高影响力观点，附 3 条原话与位置。
- **证据**：每类至少 1 条，再按影响力补足 10 条；保留标题、链接、摘要、引用位置、情绪。
- **风险**：使用数据集中人工编写的风险点，动态附加命中的来源引用与数量，按 high/medium/low 排序；综合评分：
  `负面占比×0.7 + 论坛负面×0.15 + 高风险数×7 + 视频负面×0.08`，映射到 高/较高/中/低。
- **结论**：综合来源数、风险等级、负面占比、主要观点群体与前两个风险点生成结论摘要、3 条建议、置信度（来源覆盖与规模）。

## 5. 报告模板

`reports/{report_id}/report.md` 固定 8 个部分：

1. 事件概述：背景、分析范围、来源结构、引用
2. 时间线：时间、事件、说明、来源引用
3. 传播渠道：类型、数量、占比、负面占比、代表来源
4. 主要观点：按角色分组，含立场、摘要、原话与引用
5. 情绪倾向：正/中/负数量与占比、整体判断、趋势
6. 风险判断：等级、描述、观察指标、关联来源、引用
7. 重点证据：编号、标题/链接、来源/类型、时间、引用位置、摘要
8. 结论摘要：结论、建议（带引用）、置信度

文末附「来源清单」：`[Sxx] | 类型 | 标题 | 来源 | 时间 | 情绪 | 链接`。所有结论至少命中一个来源编号，可回溯到来源记录、论坛日志或图谱节点。

同时保存 `report.json`（前端渲染）、`search.json`（主题词、执行时间、来源摘要、分析输出、步骤、多媒体指标）与 `meta.json`（列表元数据）。

## 6. 图谱模型

```json
{
  "report_id": "RPT-20261024-161955-057C",
  "topic": "预制菜进校园",
  "nodes": [
    {
      "id": "TOPIC",
      "label": "预制菜进校园",
      "type": "topic",
      "source_refs": ["S01", "S02"],
      "description": "...",
      "degree": 37
    }
  ],
  "edges": [
    {
      "id": "EDGE-001",
      "source": "TOPIC",
      "target": "E01",
      "relation": "contains",
      "label": "包含事件",
      "source_refs": ["S05", "S19"]
    }
  ],
  "stats": {
    "node_count": 51,
    "edge_count": 91,
    "type_counts": {},
    "relation_counts": {}
  }
}
```

- 节点类型：`topic / brand / event / person / org / media / source`；
- 关系类型：`contains / spread_by / reports / illustrates / covers / discusses / supports / mentions / involves / published / affiliated_with / participates_in / operated_by / regulates / supervises / administers / inspects / standardizes / cooperates_with / related_brand / produced_by / supplies / serves / values`；
- 节点与边都必须带 `source_refs`，来源节点只收录证据与高影响力来源（默认最多 18 个），避免图谱不可读；
- 查询：`POST /api/graph/query` 支持 `report_id`、`node_type`、`keyword`、`relation`、`source_ref`、`limit`；只返回命中的节点/边及统计。

### 前端布局

- 力导向：确定性初始位置 + 类型锚点 + 斥力/弹簧/向心约束 200 次迭代，按类型分布在左（事件）→中（机构/人物/品牌）→右（媒体/来源）；
- 分层：topic / event / org·person·brand / media / source 五列；
- 节点半径按类型和度数，颜色按类型；点击节点高亮关联边、显示关系标签与侧栏属性；画布支持拖拽平移与滚轮缩放；
- 来源节点默认不显示标签（点击或在分层布局下显示），避免 18 个来源标签重叠。

## 7. WebSocket 协议

`/api/ws` 接受连接后先发 `hello`，随后事件格式统一带 `type`、`ts`、`seq`：

| 类型 | 必含字段 | 触发 |
| --- | --- | --- |
| `app_status` | `app_name`、`status` | 应用状态流转 |
| `app_output` | `app_name`、`output_text` | 任务输出写入 |
| `forum_log` | `message_text`、`task_status` | 论坛采集日志 |
| `system_status` | `system_status`、`running_apps` | 系统启停 |
| `graph_ready` | `report_id`、`graph_path` | 图谱落盘 |
| `error` | `module_name`、`error_message` | 业务异常/采集异常 |

前端连接失败或断开时自动每 2.5 秒重连；连接不可用时控制台、论坛、状态页降级为 3-5 秒轮询。

## 8. 配置管理

`config.json` 分四段：`system`、`collection`、`runtime`、`apps`，`app/config.py` 内定义 Schema（类型、范围、标签、提示）供前端渲染表单。

- `GET /api/config` 返回配置、Schema、`updated_at`；
- `POST /api/config` 支持部分更新，做范围/类型校验，失败返回 400 与具体错误，不写盘；
- 保存采用临时文件 + `os.replace` 原子写入；
- 保存后触发 `ProcessManager.config_changed`：
  - 记录 `runtime/system.log`；
  - 若应用中 `apps.{name}=false` 且正在运行，立即停止该应用并记录错误事件；
  - 论坛线程每轮重新读取 `collection`，采集间隔修改无需重启；
- 前端读取后渲染 4 段表单与原始 JSON 面板，保存后提示变更字段。

## 9. 接口与页面

- 18 个核心接口 + `GET /api/health` + `WS /api/ws`，另提供报告下载、报告列表、主题目录、系统日志等辅助接口；
- `/`、`/graph-viewer`、`/graph-viewer/{report_id}` 均返回单页应用，前端按路径自动定位图谱；
- `/docs` 为离线自绘文档，不依赖 Swagger CDN，包含接口分组、参数、响应示例、存储布局与调用示例。


## 11. 可靠性与测试

- 路径参数使用正则白名单，报告编号与日期校验，避免路径穿越；
- 报告、图谱、配置、论坛历史使用原子写入或行追加，避免半写文件；
- 测试 `tests/test_api.py` 使用 `create_app(tmp_path)`，覆盖健康、状态机、检索与落盘、图谱查询、论坛日志/历史、配置、系统启停、页面路由与 WebSocket；
- 前端对接口失败显示明确错误与重试按钮，不静默失败。

## 12. 已知限制

- 样例数据为离线构造，新闻/论坛链接为虚构演示地址；
- 不使用真实爬虫、情感模型或大模型，情绪与观点为规则化聚合；
- 图谱节点过多时标签会适度省略，需点击节点查看完整信息；
- 论坛采集为线程模拟，非真实论坛接口；
- 运行数据保存在本地文件，未引入数据库与分布式部署。
